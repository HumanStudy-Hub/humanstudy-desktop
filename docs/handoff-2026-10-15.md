## 3. To do, in priority order

### P0 · CPU runaway (found 2026-10-15)
Two renderer processes of a HumanStudy Hub build launched from a mounted dmg (`/Volumes/HumanStudy
Hub`, a dogfood build from ~3 days earlier) ran **~460% CPU each for 3 days** (load average 110–140).
The owner killed them before a sample was taken; cause unknown. Suspects, in order:
1. rrweb replay capture (`renderer/replay.ts`, `capture.ts`): every DOM mutation recorded and
   gzip-compressed (fflate) on the renderer thread every 10 s / 500 KB — mutation storms during
   streaming or a growing backlog could saturate it.
2. A render/resize loop: PDF re-render on panel resize (`SourceDrawer.tsx`), artifact live refresh,
   simulation progress polling.
3. No single-instance lock (two instances were running).

Do: reproduce with v0.6.0 + the sample project (idle 15 min, then one agent turn; watch renderer
CPU), take a Chrome performance profile via `--remote-debugging-port`; fix (compress in a worker /
main process, cap and throttle replay, pause when hidden/idle); add `app.requestSingleInstanceLock`;
add a watchdog event when a renderer stays hot. Ship in 0.6.1.

## Codex follow-up · interaction-only collection (2026-10-15)

Owner changed the collection policy: semantic interactions and timings, not full-window recording
or mouse trajectories. Current work is based on `hsd-verify` main (including the local simulation
redesign), not the outdated `humanstudy-desktop` checkout.

- Removed rrweb startup and its package dependencies. The compatibility entry point is inert.
- Disabled replay IPC in preload and main. New page recordings are neither accepted nor stored.
- Existing pending recordings stay local for export; automatic upload skips them. Complete
  transcript/artifact blobs still upload without truncation. Historical cloud data is untouched.
- Database migration **20261015223220_disable_desktop_session_recordings** applied to
  `zigbuogyerivbnxtnjjw`: restrictive policies block chunk-row INSERT and non-blob object
  INSERT/UPDATE in `desktop-replays`, including older clients. Existing owner checks, reads,
  exports and other buckets stay in place. Policy metadata and path predicates verified;
  no real user data was inserted/deleted to test it.
- Added a single-instance lock; second launch focuses the existing window instead of starting
  another renderer/kernel/telemetry pipeline.
- Agreement wording describes interactions plus research content and explicitly excludes page
  recordings and mouse movement. Removed the outdated self-service deletion promise.
- 65 desktop regression tests pass with localhost fixture permission; node/web typechecks and
  production build pass. New tests cover disabled recording ingress, retained historical local
  chunks, complete blob uploads and rejection of movement/keystroke stream events.
- CPU root cause remains unproven. Removing the suspected recorder and duplicate-instance path
  is mitigation, not proof of the original three-day runaway cause. Long-duration live sample,
  streaming, PDF resize and simulation profiling remain required before declaring it resolved.
- These desktop changes are not yet in an installed/notarized 0.6.1 build. Server-side blocking is
  already active, but users on 0.6.0 must upgrade to stop local recording and its potential CPU cost.

Migration source is in the web repo at
`supabase/migrations/20261015223220_disable_desktop_session_recordings.sql`.
Do not apply the unrelated untracked offline-capture migration as part of this change.

### CPU follow-up: 0.6.1 candidate

Two concrete hotspots were reproduced and fixed after retiring replay: every-width PDF raster
painting, and every-chunk growing-message rendering. PDF painting now waits for settled width
and pauses outside the viewport; visited text layers stay mounted so selection survives scroll.
Text display batches at 100 ms with immediate ordered flush around questions/tools/completion;
complete main-process persistence is unchanged. The candidate version is 0.6.1.

70 final regression tests pass. Two isolated launches of the actual main process confirmed
one lock winner, one rejected secondary process and one existing window. CPU sampling of the
built renderer showed long-stream non-idle samples falling from 77.59% to about 19%; CPU returned
to low idle after work stopped. The exact three-day incident remains historically unproven.
See `docs/verification/cpu-2026-10-15.md` and `app/scripts/profile-renderer.cjs` for evidence and
reproduction. A final 15-minute fixture progress soak and Mac notarization are still in progress;
