# Renderer CPU investigation · 2026-10-15

The original two renderer processes were killed before a stack sample was collected. Their
three-day ~460% CPU incident cannot be assigned a definitive historical cause. The following
are reproduced performance defects, with fixes and repeatable measurements, rather than a
claim that every possible future CPU issue has been eliminated.

## Reproduced and fixed

1. PDF comparison resizing started a new raster render for every observed width. The sample
   produced 1,008 new canvas renders during 20 seconds of scheduled width changes. The fix
   immediately cancels stale painting, scales the existing bitmap with CSS while dragging,
   and redraws visible pages after 120 ms of stable width. Far-away/hidden canvases stop
   painting; visited text layers stay mounted to preserve cross-page selections.
2. Every incoming text batch re-rendered the growing reply, including Markdown parsing,
   sanitizing and DOM/layout work. The fixture streamed five chunks every 25 ms. Grouping
   adjacent chunks for at most 100 ms reduces rendering frequency without shortening text.
   Tools, questions, permissions, errors and completion flush preceding text immediately;
   switching projects/threads cancels stale UI buffers. Every event still reaches main immediately; its complete transcript collection and existing
   persistence path are unchanged.
3. Full DOM/mouse capture was retired in desktop PR #1; the server blocks legacy uploads
   (web PR #21). A native two-launch test confirmed one primary lock, one secondary rejection,
   one existing-window notification and one window. No real account or project was used.

## Measurements

The actual built React renderer, bundled PDF worker and shipped Knobe paper ran in an isolated
Electron fixture. It has temporary userData, fixture account/kernel, blocked external network,
a hidden window with background throttling disabled, and Chromium CPU profiles per phase.

| 20-second phase | Before: non-idle main-thread samples | After: non-idle main-thread samples |
|---|---:|---:|
| PDF idle | 0.19% | 0.16% |
| Continuous PDF resizing | 57.35% | 22.98% |
| Idle after resizing | 0.08% | 0.22% |
| Long text stream | 77.59% | 19.46% |
| Idle after text stream | 0.07% | 0.10% |

These are sampling shares, not Activity Monitor percentages. Random widths and timer scheduling
vary between runs. The final stream delivered 3,915 chunks; its last chunk was visible after
completion. The final resize run started at three canvas draws and ended at nine after settling: six
additional draws versus 1,008 before (about 99% fewer). Short stable gaps during the scheduled
drag caused three of those draws; three visible pages were painted after the final width settled. The remaining resize cost includes browser
layout/CSS scaling. This intentionally avoids rerasterizing the whole PDF while dragging.

The first comparison's simulation phase did not load its result iframe because of the normal
application CSP. Its numbers are excluded. The reusable harness relaxes only its fixture HTML's
frame-src to allow its localhost result artifact, then writes synthetic progress once a second
through the fixture project API. Production CSP is unchanged.

## Verification and reproduction

- 70 regression tests passed, including Unicode stream completeness, ordering around questions /
  tools / completion, timer cancellation, and settled/hidden PDF rendering.
- Node/web typechecks and production build passed.
- Final-source 15-minute live-progress soak passed: 900 one-second samples, with no sustained
  CPU climb. Electron-reported aggregate renderer CPU averaged 0.092%, peak 0.843%;
  first-minute mean 0.099%, last-minute mean 0.094%. These reported metrics are not
  directly comparable to Activity Monitor process percentages.
- Both Apple Silicon and Intel apps signed/notarized/stapled; Gatekeeper accepted. DMG integrity,
  updater SHA-512 metadata and packed renderer equality checks passed.
- Multi-page selection remained connected after scrolling off-screen; the completed stream
  retained its last chunk.
- 0.6.1 candidates are in app/dist/v0.6.1-candidate-20261015. No public release, tag push,
  updater rollout or installed-app replacement was performed.

From the desktop app directory after installing dependencies:

```sh
npm run build
PERF_SOAK_SECONDS=900 ./node_modules/.bin/electron scripts/profile-renderer.cjs
```

Set PERF_OUT to choose an output directory. Outputs are phase `.cpuprofile` files, phase JSON
counters, `report.json`, and minute-level `soak-progress.json`. The harness does not connect to
the hosted agent or upload research data. A timeout bounds the fixture lifetime. It also checks
that the last streamed chunk is displayed and cross-page selection survives scrolling.

Local investigation artifacts: `/private/tmp/hs-cpu-baseline3`, `/private/tmp/hs-cpu-final`;
final source soak: `/private/tmp/hs-cpu-selection-final`.


## Recorder control

As an isolated negative control, the retired recorder was enabled only in the fixture on top of
the optimized renderer, with upload disabled. The short run completed, returned to low idle,
and did not reproduce persistent high CPU (stream non-idle samples: 21.66%; idle after stream:
0.11%). This is not the old three-day binary and cannot rule out a recording backlog under a
longer or different workload. No real user recording was made. Upstream also documents
[mutation-processing costs in complex pages](https://github.com/rrweb-io/rrweb/issues/1447);
that supports investigating the recorder but does not establish the historical cause.
